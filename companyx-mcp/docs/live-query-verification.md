# 실시간 조회 검증 — "정답을 외운 게 아니라, 실데이터를 조회한다"

## 검증 목적

시스템이 예시 질문 30개의 **정답을 암기해 뱉는 것**인지, 아니면 매 질문마다
**실제 데이터베이스·그래프를 조회해 답을 계산**하는 것인지 확인한다.

## 방법

`questions.json`(예시 30문항)에 **없는 새 질문**을 던진다. 암기라면 답할 수 없고,
실시간 조회라면 정답이 나온다. 정답은 데이터셋 원본을 직접 계산해 대조한다.

## 결과 — 2개 모두 정확히 일치

| 질문 (30문항 외) | 데이터 직접 계산 (정답) | 시스템(gemma4:e2b) 답 | 일치 |
|---|---|---|---|
| 대전 지역 매출 총액은? | **64,366** (매출 91건 합산) | 64,366 | ✅ |
| Product-C2를 사용하는 고객사는? | Client-D·B·F·X·G·H (6개) | Client-D·B·F·X·G·H (6개) | ✅ (순서까지) |

## 왜 이것이 "암기 아님"의 증거인가

- **대전 64,366** 은 매출 테이블 **91개 행을 실시간으로 합산**한 값이다.
  이런 수치는 외울 수 없다 — 시스템이 `SELECT SUM(amount) FROM sales WHERE region='대전'`
  형태의 SQL을 생성해 **실제 PostgreSQL을 조회**한 결과다.
- **Product-C2 고객사** 는 지식 그래프의 실제 `USES` 관계를 순회해 얻은 결과다.
- 정답이 코드·프롬프트에 저장돼 있지 않다. **데이터를 바꾸면 답도 바뀐다.**

→ 결론: **암기가 아니라 실시간 데이터 조회.** 미지의 질문에도 실데이터로 답한다.

## 응답 속도에 관하여

느린 구간은 **데이터 조회가 아니라 LLM 추론**이다.

| 단계 | 소요 | 비고 |
|---|---|---|
| DB 조회 / 그래프 순회 | 수 ms | 병목 아님 |
| LLM(gemma) 생성 ×1~2회 | 수 초 | 질문→조회스펙, 조회결과→자연어 답변 |
| 첫 질문(콜드 스타트) | 20초+ | 7.2GB 모델을 메모리에 로딩하는 시간 포함 |
| 연속 질문(웜) | 1~2초 | 30문항 연속 평가 시 실측 |

**속도 개선 수단**: `OLLAMA_KEEP_ALIVE`로 모델 상주, GPU 활용, 더 작은 모델.
로컬 온프레미스 특성상 질문당 수 초는 정상 범위이며, **정확도를 우선한 트레이드오프**다.

## 한 줄 결론

> 예시 30문항 밖의 질문(대전 매출 총액, Product-C2 사용 고객사)도 실데이터에서
> 정확히 계산해 답한다. **암기가 아닌 실시간 조회**이며, 응답 지연은 로컬 LLM 추론
> (특히 콜드 스타트) 때문으로 모델 상주·GPU로 단축 가능하다.
